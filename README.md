# net-speedmeter

[![CI](https://github.com/scrollDynasty/net-speedmeter/actions/workflows/ci.yml/badge.svg)](https://github.com/scrollDynasty/net-speedmeter/actions/workflows/ci.yml)

Консольная утилита для замера скорости интернета. Скачивает тяжёлый файл (по умолчанию — фотографию
14.7 MB) 10 раз подряд и печатает среднее время запроса, объём скачанных данных и скорость в MB/s.

> **Тестовое задание:** «Написать скрипт-замерятель скорости интернета со своего компьютера. Он должен принимать адрес,
> куда стучаться (какая-нибудь тяжелая картинка), запускать последовательно 10 запросов к этому адресу, дожидаться
> ответа, вычислять среднее время запроса, объем скачанных данных и печатать в консоли скорость мб/с.»

| Требование | Где в решении |
|---|---|
| принимает адрес | аргумент `URL` (по умолчанию — картинка с Wikimedia Commons) |
| 10 последовательных запросов | `-n 10` по умолчанию, строго по одному, каждый ответ дочитывается до конца |
| среднее время запроса | строка `Avg request time` |
| объём скачанных данных | строка `Downloaded` |
| скорость, мб/с | строка `Speed`: в MB/s и в скобках в Mbit/s, поскольку «мб/с» допускает оба прочтения |

## Запуск

Нужны Python 3.11+ и [uv](https://docs.astral.sh/uv/) (`pip install uv`). Единственная прямая зависимость —
httpx; `uv run` ставит ещё и инструменты разработки (без них — `uv run --no-dev`).

```bash
git clone https://github.com/scrollDynasty/net-speedmeter.git
cd net-speedmeter
uv run net-speedmeter -n 3       # быстрая проверка: 3 запроса
uv run net-speedmeter            # полный замер по ТЗ: 10 запросов, ~150 MB, на медленном канале — минуты
uv run net-speedmeter "https://speed.cloudflare.com/__down?bytes=25000000"   # другой источник
```

<details>
<summary>Без uv</summary>

```bash
python -m venv .venv
source .venv/bin/activate        # Git Bash на Windows: source .venv/Scripts/activate
                                 # PowerShell: .venv\Scripts\Activate.ps1
pip install .
net-speedmeter -n 3              # или: python -m net_speedmeter -n 3
```

</details>

Параметры: `URL` (только `http`/`https`) и `-n` — число запросов от 1 до 1000.
Коды выхода: `0` — все запросы успешны, `1` — хотя бы один завершился ошибкой, `2` — неверные аргументы,
`130` — прервано через Ctrl+C (сводка печатается по завершённым запросам).

`Speed` — общий объём / общее время всех успешных запросов. `Without #1` — то же без первого запроса:
он открывает соединение (DNS, TCP, TLS), и TCP ещё не вышел на полную скорость. Если адрес
перенаправляет, то после первого успешного запроса остальные идут сразу на конечный адрес — иначе каждый
запрос платил бы за лишний переход. Для файла меньше 1 MB утилита предупреждает, что результат
отражает в основном задержку, а не скорость канала.

## Методика

- **Время** — по `time.perf_counter()`. Время запроса — от начала запроса до последнего байта тела ответа;
  TTFB (time to first byte) — до получения заголовков ответа (близко к `time_starttransfer` в curl).
  На новом соединении оба значения включают DNS, TCP, TLS и переходы по редиректам.
- **Объём** — байты тела ответа в том виде, в каком они пришли по сети (`num_bytes_downloaded` в httpx,
  до распаковки), без заголовков и служебных байтов TLS/TCP. Запрос идёт с `Accept-Encoding: identity`,
  чтобы сжатие не исказило объём; тело читается потоком и не хранится в памяти.
- **Скорость = Σ байтов / Σ времени запросов** — то же, что «средний объём / среднее время запроса».
  Среднее скоростей отдельных запросов завышает результат: 10 MB за 1 с и 10 MB за 9 с — это 2 MB/s,
  а среднее двух скоростей дало бы 5.6 MB/s.
- **Ошибки.** Ответ с кодом не 2xx или обрыв соединения (в том числе раньше, чем пришло `Content-Length`
  байт) — неуспешный запрос: он виден в выводе и влияет на код выхода, но не попадает ни в средние,
  ни в `Downloaded`. Небольшое тело ответа с ошибкой (до 64 KiB) дочитывается, чтобы соединение
  переиспользовалось дальше.
- **Единицы** десятичные, как у провайдеров: 1 MB/s = 10⁶ байт/с = 8 Mbit/s.
- **Клиент** передаёт User-Agent с адресом репозитория (без него Wikimedia
  [отвечает 403](https://foundation.wikimedia.org/wiki/Policy:User-Agent_policy)) и `Cache-Control: no-cache`.
  Параметр для обхода кэша CDN в URL сознательно не добавляется: иначе каждый запрос нагружал бы
  исходный сервер Wikimedia.
- **Ограничения:** один поток и одно соединение, как в ТЗ (при редиректе на другой хост — два);
  измеряется скорость до конкретного сервера; прокси из `HTTP(S)_PROXY`/`ALL_PROXY` учитываются;
  только HTTP/1.1 и только скачивание; таймаут — 30 с на подключение и на каждое чтение, а не на весь файл.

## Где это пригодится в арбитраже

Для арбитража важны не MB/s на 15-мегабайтном файле, а TTFB и загрузка лендинга весом 1–3 MB: на
мобильном 3G/4G в tier-3 гео каждая лишняя секунда снижает CR и поднимает CPA. Утилита скачивает только
сам документ, без картинок и скриптов страницы, но проходит по HTTP-редиректам: TTFB первого запроса на
трекерную ссылку включает все переходы цепочки трекер → преленд → оффер (печатается конечный адрес).
Остальные запросы идут уже на конечный адрес, а JS- и meta-редиректы утилита не видит.

Замер из дата-центра или через прокси показывает их канал, а не канал мобильного пользователя, а проверки
трекерных ссылок попадают в статистику кликов — для них нужна тестовая кампания или фильтр по User-Agent.
Ядро (`net_speedmeter.measure.benchmark`) не зависит от CLI; в задаче Celery результаты нужно собрать
в список и задать лимит времени задачи: таймаут здесь — на каждое чтение, а не на весь файл.

## Разработка

```bash
uv sync
uv run pytest --cov              # unit-тесты на httpx.MockTransport + интеграционные на локальном HTTP/1.1-сервере
uv run ruff check . && uv run ruff format --check . && uv run mypy
```

CI: ruff, mypy в строгом режиме и тесты на Ubuntu (Python 3.11 и 3.13) и Windows.

## Как использовался AI

Решение написано с помощью Claude Code; задачи ставил и результат проверял я. Методику сверил с исходниками
httpx и описанием Cloudflare Speed Test, цифры — с curl: на файле Cloudflare 25 MB при поочерёдных запусках
curl показал 2.2–4.1 MB/s, net-speedmeter — 3.0–4.4 MB/s, то есть в пределах колебаний канала.

Затем я отдал решение на ревью (код, методика, тесты с мутационным тестированием, приёмка с нуля) — тоже
силами AI-агентов. Найденное:

| Проблема | Исправление |
|---|---|
| Несуществующий тег `astral-sh/setup-uv@v10` в CI | action закреплён на SHA коммита |
| Ответ с ошибкой закрывал keep-alive, и следующий запрос снова был «холодным» | тело ошибки дочитывается, есть тест на реальном сервере |
| Редирект повторялся в каждом запросе и попадал во время замера | после первого запроса используется конечный адрес |
| Чтение блоками по 256 KiB «для эффективности» на локальном сервере (~2 Gbit/s, медиана 12 запросов) оказалось на ~25 % медленнее | убрано |
| Собственная проверка `Content-Length` (с багом: `str.isdigit()` пропускал `"²"`) дублировала проверку в httpx | убрана целиком |
| Падение на URL с не-ASCII символами при выводе в файл на Windows | файлы пишутся в UTF-8, есть тест |
| Ложная строка «redirected to», когда httpx лишь нормализовал URL | редирект определяется по `response.history` |

Не всё предложенное принял. Первая версия была заметно больше: Typer + Rich, прогресс-бар, `--json`,
Docker, шесть кодов выхода, перцентили. Ревью показало, что для скрипта из ТЗ это лишнее, и я сократил
решение до одной зависимости и ~300 строк кода вместе с докстрингами, сохранив методику и тесты.
