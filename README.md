# net-speedmeter

[![CI](https://github.com/scrollDynasty/net-speedmeter/actions/workflows/ci.yml/badge.svg)](https://github.com/scrollDynasty/net-speedmeter/actions/workflows/ci.yml)

Консольный замерятель скорости интернета. Скачивает тяжёлый файл (по умолчанию фотографию 14.7 MB)
**10 раз подряд** и печатает среднее время запроса, объём скачанных данных и скорость в **MB/s**
(рядом — в Mbit/s).

> **Тестовое задание:** «Написать скрипт-замерятель скорости интернета со своего компьютера. Он должен принимать адрес,
> куда стучаться (какая-нибудь тяжелая картинка), запускать последовательно 10 запросов к этому адресу, дожидаться
> ответа, вычислять среднее время запроса, объем скачанных данных и печатать в консоли скорость мб/с.»

| Требование | Где в решении |
|---|---|
| принимает адрес | аргумент `URL` (по умолчанию — картинка с Wikimedia Commons) |
| 10 последовательных запросов | `-n 10` по умолчанию, строго по одному, каждый ответ дочитывается до конца |
| среднее время запроса | строка `Avg request time` |
| объём скачанных данных | строка `Downloaded` |
| скорость, мб/с | строка `Speed`: в MB/s и в Mbit/s, поскольку «мб/с» допускает оба прочтения |

## Запуск

Нужен Python 3.11+ и [uv](https://docs.astral.sh/uv/) (`pip install uv`).

```bash
git clone https://github.com/scrollDynasty/net-speedmeter.git
cd net-speedmeter
uv run net-speedmeter -n 3       # быстрая проверка: 3 запроса к картинке по умолчанию
uv run net-speedmeter            # полный прогон по ТЗ: 10 запросов, ~150 MB
uv run net-speedmeter "https://speed.cloudflare.com/__down?bytes=25000000"   # другой источник
```

На медленном канале полный прогон до Wikimedia может занять несколько минут.

## Параметры

| Параметр | По умолчанию | Описание |
|---|---|---|
| `URL` | картинка 14.7 MB | что скачивать, только `http`/`https` |
| `-n, --count` | `10` | число последовательных запросов (1–1000) |
| `--timeout` | `30` | таймаут в секундах на подключение и на каждое чтение |
| `--no-keepalive` | — | новое соединение на каждый запрос |
| `--json` | — | полный машиночитаемый отчёт, в том числе перцентили скорости |

Коды выхода:
- `0` — успех;
- `1` — часть запросов завершилась ошибкой;
- `2` — неверные аргументы;
- `3` — все запросы завершились ошибкой;
- `4` — ошибка окружения (например, неверный `HTTPS_PROXY`);
- `130` — прервано через Ctrl+C, сводка печатается по завершённым запросам.

## Методика

**Время**
- Берётся из `time.perf_counter()`.
- **Время запроса** — от начала запроса до последнего байта тела.
- **TTFB** — до получения заголовков ответа, аналог `time_starttransfer` в curl.
- На новом соединении оба значения включают DNS, TCP и TLS.

**Объём**
- Это байты тела HTTP в том виде, в каком они пришли по сети: `num_bytes_downloaded` в httpx, до распаковки.
  Заголовки и служебные байты TLS/TCP не считаются, как и в `size_download` у curl.
- Запрос идёт с `Accept-Encoding: identity`, чтобы сжатие не исказило объём.
- Тело читается потоком и не хранится в памяти.

**Скорость = Σ байтов / Σ времени запросов**, а не среднее скоростей отдельных запросов.
- Это то же, что «средний объём / среднее время запроса».
- Простое среднее завышает результат. Пример: 10 MB за 1 с и 10 MB за 9 с — это 20 MB за 10 с, то есть 2 MB/s,
  а среднее двух скоростей дало бы 5.6 MB/s.

**Ошибки**
- Ответ не-2xx, обрыв соединения или несовпадение `Content-Length` с полученным объёмом — неуспешный запрос.
- Такие запросы видны в выводе и влияют на код выхода, но не попадают ни в средние, ни в `Downloaded`.

**Единицы** десятичные, как у провайдеров: 1 MB/s = 10⁶ байт/с = 8 Mbit/s.

**Клиент**
- Передаёт User-Agent с адресом репозитория. Wikimedia [требует его](https://foundation.wikimedia.org/wiki/Policy:User-Agent_policy)
  и без него отвечает 403.
- Шлёт `Cache-Control: no-cache`. Параметр для обхода кэша CDN к URL сознательно не добавляется: иначе каждый
  запрос нагружал бы исходный сервер Wikimedia.

Чем больше файл, тем меньше на результат влияют задержка и разгон TCP. Для каналов быстрее 100 Mbit/s
лучше брать от 25 MB: `https://speed.cloudflare.com/__down?bytes=N` (N < 10⁸) или
`https://nbg1-speed.hetzner.com/100MB.bin`.

**Ограничения**
- Один поток и одно соединение, как в ТЗ.
- Измеряется скорость до конкретного сервера, а не «интернета вообще».
- Если задан `HTTPS_PROXY`, замер пойдёт через прокси.
- Только HTTP/1.1 и только скачивание.
- Прогресс-бар обновляется во время замера; на скоростях от ~1 Gbit/s это заметно, тогда лучше `--json`.

## Как устроено

| Модуль | Назначение |
|---|---|
| `measure.py` | сеть (httpx), генератор результатов по одному запросу |
| `stats.py` | агрегация, чистые функции без ввода-вывода |
| `models.py` | неизменяемые dataclass-ы; `to_dict()` даёт те же блоки, из которых собран `--json` |
| `cli.py` | Typer + Rich, только представление |

Ядро не зависит от CLI, поэтому его можно вызвать из задачи Celery или management-команды Django:

```python
from net_speedmeter import iter_benchmark, summarize

summary = summarize(list(iter_benchmark("https://cdn.example.com/creative.jpg", count=3)))
summary.throughput  # байт/с, None если все запросы упали
summary.to_dict()  # для JSONField / результата задачи
```

Так это могло бы стать мониторингом скорости отдачи лендингов и креативов по гео (не реализовано):
- задача Celery по расписанию;
- результат в PostgreSQL;
- отдельный воркер в каждом гео. Через прокси измерится канал прокси, а не то, как CDN отдаёт контент в этом регионе.

У такого мониторинга есть цена: каждая проверка — это реальный трафик CDN. При настройках по умолчанию
(10 × 15 MB) это ~150 MB на одну цель в одном гео. Для мониторинга хватит файла 1–2 MB и 2–3 запросов,
а если важна только задержка — одного TTFB.

## Разработка

```bash
uv sync
uv run pytest --cov        # 107 тестов, покрытие ~99%
uv run ruff check . && uv run ruff format --check . && uv run mypy
```

**Тесты.** Помимо unit-тестов на `httpx.MockTransport` есть интеграционные: они поднимают настоящий локальный
HTTP/1.1-сервер и на реальных сокетах проверяют переиспользование соединения и обрыв ответа.

**CI** гоняет ruff, mypy в строгом режиме и тесты на Ubuntu/Windows с Python 3.11–3.13, а также на macOS.
Отдельная джоба проверяет минимальные заявленные версии зависимостей, ещё одна собирает Docker-образ.

## Как использовался AI

Решение написано с Claude Code. Я ставил задачи, проверял результат и принимал решения.

**Сверка методики и цифр**
- Методику сверил с исходниками httpx и описанием Cloudflare Speed Test.
- Цифры сверил с curl: на файле Cloudflare 25 MB при поочерёдных запусках curl показал 2.2–4.1 MB/s,
  net-speedmeter — 3.0–4.4 MB/s. Расхождение в пределах колебаний канала.

**Ревью первой версии.** Её я отдельно прогнал через ревью кода, архитектуры, методики и тестов (с мутациями),
тоже с помощью AI-агентов. Что нашлось:

| Что было | Что сделано |
|---|---|
| В CI указан несуществующий тег `astral-sh/setup-uv@v10`, первый прогон упал | action закреплён на SHA коммита |
| Минимальная версия `typer>=0.15` на деле не работала | исправлено, CI теперь проверяет минимальные версии |
| Чтение чанками по 256 KiB «для эффективности» на замере оказалось на ~25% медленнее | убрано |
| `str.isdigit()` при разборе `Content-Length` пропускал `"²"` и падал | заменено |
| Округление печатало `1000.00 kB` | исправлено |
| Мутационное тестирование нашло изменения логики, которые не ловил ни один тест | добавлены тесты |

Не всё предложенное я принял. Ограничение размера ответа, общий дедлайн, запрет редиректов https→http,
Dependabot и подробная статистика в выводе для утилиты на один запуск лишние. Подробная статистика
осталась только в `--json`.

Первые шесть коммитов сделаны одной серией после написания кода, дальнейшие — по ходу исправлений.
